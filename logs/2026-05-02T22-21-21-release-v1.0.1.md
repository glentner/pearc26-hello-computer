new comprehensive workflow in commit `7adccf4`.

I followed the on-disk version because:

1. The user's argument shape (`v1.0.1 with tag and release`) is the
   explicit-version-with-release pattern from the new skill, not the
   old one.
2. The old skill's first step (`Verify the current branch is main`)
   would have aborted immediately (we were on `wip`), and that abort
   would have asked the user to do exactly what the new skill
   handles automatically.
3. The path in the invocation header pointed to the on-disk file,
   which had been updated.

Worth flagging for future skill iterations: invocation messages can
carry pre-edit snapshots. If on-disk and invocation-message versions
disagree, prefer the on-disk version after sanity-checking that the
user's arguments and current state make sense for it.

## Skill Refinement Candidates (for the next iteration)

A few small refinements surfaced during the run; none blocking, all
recordable for a future polish pass on the skill:

- **`gh` upgrade chatter pollutes output**. `gh release view` and
  `gh release create` prepend an "A new release of gh is available"
  banner that has to be filtered. The skill could mention setting
  `gh config set --host github.com prompt disabled` or piping through
  `grep -v` for cleaner agent parsing.
- **filter-branch deprecation warning**. Documented in the skill's
  Step 3 note; the warning still appears in output. Setting
  `FILTER_BRANCH_SQUELCH_WARNING=1` inline would silence it without
  changing semantics. Not critical.
- **Force-push on wip was a no-op-equivalent in this case**. Origin
  had no divergent commits; a normal push would have worked. Skill
  always force-pushes, which is correct in general (the prefix
  rewrite usually creates divergence), but worth a note that the
  force flag is a safety blanket more than a strict necessity.
